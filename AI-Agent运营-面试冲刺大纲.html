03大模型核心概念卡片能用自己的话讲出来即可

下面 12 张卡是这类岗位的「认知及格线」。不要背定义，要能说出它解决什么问题、什么时候用。

Token

模型处理文本的最小单位，中文约 1 字 ≈ 1–1.5 token。计费、上下文长度、响应速度都按它算。

上下文窗口

模型一次能「看到」的 token 上限。超了要截断或做摘要。越长越贵、越慢，不是越大越好。

Temperature

控制随机性，0–2。低（0–0.3）稳定适合客服/抽取；高（0.7+）发散适合创意。做 Agent 通常调低。

幻觉 Hallucination

模型一本正经地编造事实。缓解手段：RAG 给资料、Prompt 约束「不知道就说不知道」、工具查询、人工兜底。

Prompt 工程

公式：角色 + 任务 + 约束 + 示例（Few-shot）+ 输出格式。复杂任务加「一步步思考」（CoT）。

RAG 检索增强

文档切块 → 向量化（Embedding）→ 存向量库 → 按问题召回 → 拼进上下文生成。解决私域知识、时效性问题。

微调 Fine-tuning

用标注数据改模型行为/风格。成本高、周期长；适合固定风格与格式，不适合天天变的知识。

Function Calling

模型输出结构化的「我要调用哪个工具、参数是什么」，程序执行后把结果回传。Agent 能查天气、查订单、发邮件全靠它。

Agent

大模型 + 规划 + 记忆 + 工具 + 循环。ReAct：思考 → 行动 → 观察 → 再思考，直到完成任务。

Workflow vs Agent

Workflow 是固定流程编排（稳、可控、便宜）；Agent 是自主决策（灵活、但易跑偏、贵）。运营要先问：这个场景真需要自主决策吗？

MCP

Model Context Protocol，把模型和外部工具/数据源标准化连接。一句话：让「接工具」变成插拔式。

效果评估

任务完成率、准确率、幻觉率、响应时延、单次成本、人工介入率、用户满意度。运营的核心工作之一就是建 badcase 库。

Agent 运行流程（画得出来就赢一半）

用户输入→ 意图理解 / 规划→ 选择工具 / 检索知识库→ 执行 & 观察结果→ 生成回答→ 兜底 / 转人工

被问「设计一个 Agent」时，就按这条链子讲，并补上「每一步的失败情况怎么处理」——这是运营和技术的区别。

# 调用大模型 API —— 面试高频，能讲清就是「真用过」
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["OPENAI_API_KEY"],   # 从环境变量读，不硬编码
    base_url="https://api.xxx.com/v1"         # 国内模型一般要改 base_url
)

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "你是电商客服，只回答退换货问题。"},
        {"role": "user",   "content": "买的衣服能退吗？"},
    ],
    temperature=0.3,      # 客服场景要稳
)
print(resp.choices[0].message.content)

会被追问的点：messages 里 role 有哪几种？（system / user / assistant / tool）· 为什么要传 system？（设定角色与规则）· 怎么控制输出 JSON？（Prompt 里给 schema + 用 response_format 或让模型输出后 json.loads）

Python 高频八股（初级只会问这些）

list 和 tuple 区别？ 可变 vs 不可变，tuple 更省、可作 dict 的 key。

深拷贝浅拷贝？ 浅拷贝只复制第一层，嵌套对象还是共享引用；深拷贝用 copy.deepcopy。

可变默认参数的坑？ def f(a=[]) 的列表会在多次调用间累积，应写 a=None 再判断。

装饰器是什么？ 不改原函数代码、给它套一层额外逻辑（如计时、重试），基于闭包。

生成器？ 用 yield 逐个产出，省内存，适合处理大文件。

05运营方法论 + 数据这才是岗位主线

AARRR 是什么？怎么用到 Agent 产品？

获取 → 激活 → 留存 → 变现 → 推荐。落到 Agent：获取=渠道投放/内容引流；激活=用户完成第一次有效对话；留存=7 日内再次使用；变现=付费/订阅；推荐=分享裂变。

Agent 的回答质量怎么评估？

四层：① 建评测集（覆盖高频 + 边界问题）；② 人工按维度打分（准确性、完整性、语气）；③ 用大模型当裁判（LLM-as-judge）批量跑分；④ 线上看任务完成率、转人工率、差评率，把 badcase 沉淀成回归测试集。

怎么判断一次改版有效？

A/B 测试：只改一个变量（如 Prompt 版本），分流用户，看核心指标（完成率/留存）差异是否显著，避免用「感觉变好了」下结论。

北极星指标怎么定？

找「用户获得价值」的那个数。客服 Agent 是自助解决率；内容 Agent 是有效产出采纳率；不是 DAU 这种虚荣指标。

运营岗的杀手锏回答：「我会先定义什么叫『好』，再用数据证明它变好了，最后把有效的做法固化成 SOP / 模板。」——这句话能同时打动技术面和业务面。

06场景题万能框架大概率现场出题

题目长这样：「如果让你给我们做一个售前咨询 Agent / 招聘筛选 Agent / 内容生成 Agent，你怎么做？」

按这 8 步讲，先讲骨架再补细节，不要一上来就讲技术：

  • ① 目标与指标
    这个 Agent 要替谁解决什么问题？成功指标是什么？
  • ② 用户与场景
    谁用、在什么渠道用、最高频的三个问题是什么。
  • ③ 能力边界
    哪些它做、哪些必须转人工——边界先划清。
  • ④ 知识来源
    产品文档、FAQ、历史聊天记录 → 清洗入库（RAG）。
  • ⑤ 流程与工具
    意图识别 → 检索 → 调工具（查库存/下单）→ 生成 → 兜底。
  • ⑥ Prompt 设计
    角色、语气、必须遵守的规则、禁止事项、输出格式。
  • ⑦ 评测与上线
    先小流量灰度，建 badcase 库，按周迭代 Prompt 与知识库。
  • ⑧ 复盘
    用数据说话：解决率、满意度、成本，再决定加功能还是砍功能。

07行为面 & 反问决定「要不要你」

为什么想做 AI Agent 运营？

别说「因为 AI 火」。说：「我喜欢把不确定的东西跑通——搭一个 Agent、看它从答错到答对，这个过程让我有成就感；而且运营能直接看到用户反馈，迭代最快。」

你最大的缺点？

说一个真实但不致命的：「工程底子不深，复杂的后端我搞不定，所以我会把边界内的脚本和配置做扎实，遇到搞不定的及时问。」 别用「我太追求完美」这种套路。

能实习多久？一周几天？

这是他们的核心顾虑。给明确数字：「一周可到岗 X 天，能稳定实习 X 个月以上。」含糊会被扣分。

期望薪资？

岗位写 4–6K，实习通常按天算。「按公司实习标准来，我更看重能接触真实业务和转正机会。」 先问清实习补贴与转正机制，别先报数。

136 个工程亮点 · 每个都是一个故事问题 → 方案 → 结果

① 动态 top_k 断崖截断，主动控制幻觉

问题：重排后固定取 top-5，有时塞了无关文档，LLM 照着编；有时真正相关的只有 2 条却硬凑 5 条。方案：把 rerank 分数 sigmoid 归一化到 0–1，找相邻分数的最大断崖（≥0.15）作为截断点，再用 min_top_k=3 兜底。一句话价值：「该给几条给几条」，从源头减少喂给模型的噪声。

② 三路检索 + RRF，解决「问的和写的不一样」

问题：用户问「怎么测电压」，文档写「直流电压测量步骤」，纯向量检索匹配差。方案：一路 hybrid 语义检索；一路 HyDE——先让 LLM 写一段「假设性答案」，再用答案去检索（措辞更接近文档）；一路 MCP 联网补实时信息。三路结果用 RRF 公式 1/(k+rank) 融合去重。被追问 HyDE 缺点：多一次 LLM 调用、有延迟和成本，且假设答案若偏了会带偏检索，所以用 RRF 和原向量路互相矫正。

③ 商品名歧义拦截，先确认再回答

问题：「万用表怎么测电压」没指明型号，直接答会张冠李戴。方案：LLM 提取商品名 → 向量库对齐 → 分数 >0.75 直接确认走检索；0.45–0.75 反问「您是问 A 还是 B？」；<0.45 直接拒绝并请用户给型号。用户回「对的 / 1」还能从历史里自动对应到上一轮选项。

④ 三层兜底，防止「误拦截」把正常问题挡掉

LLM 没提取到商品名 → 用 Milvus 子串匹配兜底（连冷门型号都能捞到）；向量对齐失败 → 用 LLM 提取结果兜底。核心思路：宁可放过让下游处理，也不要在入口把用户问题误杀。这是我在代码里加的防御性逻辑。

⑤ LLM 输出格式漂移，用正则剥离代码块围栏

坑：换模型或 API 升级后，LLM 偶尔把 JSON 包在 ```json … ``` 里返回，直接 json.loads 就崩。修：解析前先正则剥掉首尾的 markdown 围栏，再反序列化，并对字段类型做校验。面试价值：说明你知道 LLM 输出不可信，工程上要做防御。

⑥ Agent 稳定性：防死循环 + 工具条件注册

max_turns=5 到顶就用最后一条消息兜底，不让 Agent 无限调工具；联网工具只在配了 MCP_DASHSCOPE_BASE_URL 时才注册，没配就不注册——避免 Agent 调用一个根本不存在的工具报错。Prompt 里用「铁律」强制工具顺序：必须先查知识库，知识库没有才准联网，冲突以知识库为准。

Q：你们为什么用三路检索，直接向量检索不行吗？

直接向量检索只解决了「语义相近」，但有两个盲区：一是用户问法和文档措辞不一致（HyDE 用假设答案搭桥），二是本地知识库没有的实时信息（MCP 联网补）。三路召回后用 RRF 融合，比单路召回率更高，而且各路异构、结果可以互相校验。

Q：RRF 融合和直接加权打分比，好在哪？k 怎么定的？

加权融合要求各路分数同分布、可比较，而向量分、稀疏分、网络分的量纲不一样，硬加权容易被某一路带偏。RRF 只用排名，对量纲不敏感，鲁棒性更好。k 是平滑系数，我们取 60，代码里也留了注释说明 k 比 weight 影响大，后续可以用一批 query 压测调。

Q：重排后为什么不直接取 top-5，要搞动态截断？

因为 top-5 是「拍脑袋」的固定值。真正相关的文档分数会聚成一团，和不相关的之间有个明显断崖。我找这个断崖来切，该 3 条就 3 条、该 8 条就 8 条，再用 min 3 / max 10 兜底。目的是给 LLM 的上下文越干净，幻觉越少。

Q：你怎么控制幻觉？结合项目具体说。

我是五层一起控：① 检索侧动态截断减少噪声；② Prompt 里写「零幻觉铁律」，知识库没有就明说，不许用训练数据补；③ 工具调用顺序强制知识库优先；④ 答案每条事实都标【知识库原文】或【网络补充】来源；⑤ 知识和网络冲突时强制以知识库 PDF 为准。

Q：你这个 Agent 和普通 RAG 问答有什么区别？

普通 RAG 是「检索一次 → 生成一次」的直线流程；Agent 是多轮循环：模型先思考要不要调用工具、调哪个，执行完把结果塞回上下文再思考，直到能回答或达到 5 轮上限。我们的 Agent 有知识库、联网、查价、对比 4 个工具，能处理「先查规格再查价格再做对比」这类需要多步的问题。

Q：为什么用 LangGraph 编排，自己写 if/else 不行吗？

可以写，但 LangGraph 让每个节点解耦、状态统一存在一个 TypedDict 里，加节点或改路由不用动别的地方；它天然支持条件边（商品名确认后短路）和并行 fan-out / fan-in（三路检索同时跑再汇合），还能用 stream 逐节点观测执行过程，调试和复盘方便很多。

Q：商品名为什么要向量对齐，LLM 直接提取不够吗？

LLM 提取的是用户口里的说法（比如「那个万用表」），但知识库里存的是标准型号（「RS-12 数字万用表」）。不对齐的话，下游检索用错名字就查不到。向量对齐就是把用户说法映射到库内标准名，再按置信度决定直接答还是反问确认。

Q：这个项目你遇到最大的坑是什么，怎么解决的？

（挑一个讲，推荐第⑤个格式漂移或第④个误拦截）比如误拦截：早期只靠 LLM 提取商品名，遇到 LLM 不认识的冷门型号，整个查询被挡在入口、用户体验很差。后来加了 Milvus 子串匹配兜底和对齐失败兜底，拦截率明显下降，正常问题不再被误杀。

Q：你们怎么评估检索/问答效果？怎么调参？

评估上：建一批带标准答案的 query 做评测集，看召回率、答案准确率、转人工/无法回答的比例。调参上：像商品名阈值 0.75 / 0.45 这些不是拍脑袋定的，是拿一批真实 query 跑全流程、看哪个阈值下「误拦截最少 + 答错最少」选出来的——这也是代码 TODO 里写明的方法。

9用大白话讲讲什么是大模型？
「可以理解成一个读过海量文字、特别会『接话』的系统。你给它一段话，它根据学过的规律一个字一个字往下猜，猜出来就是回答。所以它很会表达、很会总结，但它不理解真假——不知道的事也可能编得很像，这就是为什么会幻觉。」
10什么是 AI Agent？和普通 AI 聊天有什么区别？★
「普通聊天是『你问一句它答一句』，它只能动嘴。Agent 是『会动手』的助手——它能自己判断要不要查资料、调哪个工具、分几步把事办完。比如用户问『这个型号多少钱、和另一个比哪个好』，它会先去知识库查规格、再查价格、再做对比，最后给结论。一句话：普通 AI 是参谋，Agent 是能跑腿的员工。」
11一个 Agent 通常由哪几部分组成？

13什么是 RAG？为什么需要它？★

14什么是幻觉？怎么减少？★
「幻觉就是 AI 不知道却编一个像模像样的答案。减少的办法我一般说四层：给它资料让它照着答（RAG）；Prompt 里明确写『不知道就说不知道，不许编』；让它调工具查真实数据；最后线上人工抽检、把答错的收集起来修。光靠换模型解决不了，得靠流程。」
15RAG 和微调怎么选？
「简单说，RAG 管『知道什么』，微调管『怎么说话、怎么做事』。知识天天变、又要能溯源，就用 RAG——改文档就行，不用重训；要统一说话风格、固定输出格式，才考虑微调。成本上 RAG 低得多，所以一般先上 RAG，不够再微调。」
16什么是 Function Calling / 工具调用？
「就是让模型能调用外部工具。你告诉它有哪些工具、每个要什么参数，模型自己判断该调哪个、把参数填好，程序执行完把结果还给它，它再组织成回答。Agent 能查订单、查价格、发邮件，全靠这个。」
17Token 和上下文窗口是什么？
「Token 是模型处理文字的最小单位，中文大概一个字等于 1 到 1.5 个 token，计费按它算。上下文窗口是一次能塞给它多少 token，超了就得截断或做摘要。它不是越大越好——越长越贵越慢，而且塞太多中间的内容反而容易被忽略。」
18Temperature（温度）是干什么的？
「控制回答的随机性，0 到 2。调低（0 到 0.3）回答稳定、每次差不多，适合客服和抽取信息；调高（0.7 以上）更发散、有创意，适合写文案。我们做 Agent 一般调低，怕它自由发挥乱来。」
19什么是多智能体（Multi-Agent）？
「就是不靠一个 Agent 干所有事，而是拆成几个各有分工的，比如一个查资料、一个写、一个检查，再由一个『主管』调度。好处是每个更专注、好维护；坏处是链路变长、成本和出错点都变多。简单场景其实没必要上，先把单 Agent 做好更划算。」
20听说过 MCP 吗？
「听过，Model Context Protocol，可以理解成 AI 界的 USB-C。以前每接一个外部系统都要单独写适配，MCP 定了一个统一标准，工具按标准暴露出来，模型或 Agent 直接插上用。它解决的是『接工具、接数据源』这件事的标准化。」
21你平时用过哪些 AI 工具或模型？各自怎么样？
「扣子我用来搭过知识库问答机器人，好处是可视化、不用写代码就能跑起来，缺点是复杂逻辑受平台限制；豆包和 Kimi 日常查资料、读长文档；写代码用 Cursor。用下来最大的感受是——模型差距没那么大，真正拉开效果的是你有没有把资料喂对、把规则写清楚。」 要点：一定要讲一个自己真用过的细节，别只报名字。

C. 产品与运营22–33

22怎么判断一个 AI Agent 产品好不好？★
「我看三层。第一，能不能把事办成——任务完成率、自助解决率；第二，办得好不好——答案准不准、语气舒不舒服、用户满不满意；第三，划不划算——响应快不快、每次调用花多少钱、有多少要转人工。只看日活或者用户说『挺好玩』是会被骗的。」
23Agent 回答得不好，你怎么定位问题？
「顺着链路一段段查：是没听懂问题（意图识别）？还是没查到资料（知识库没有或检索没召回）？还是查到了但没用上（Prompt 没让它参考）？还是模型本身能力不够？看每一步的中间结果，找到断点再改。最忌讳一上来就说『换个更强的模型』，多数问题其实在前面几步。」
24怎么评估一个 Agent 的效果？指标有哪些？★
「我分两层。离线先建一批标准问题和标准答案，看准确率、召回率、答不出来的比例；上线看真实的——任务完成率、转人工率、差评率、平均响应时间、单次成本。再用大模型批量给回答打分做初筛，人只看低分的和有争议的。关键是要有一套固定的评测集，不然每次改完都靠感觉。」
25什么是 badcase？你怎么用它？★
「就是用户真实遇到、Agent 答错或答得不理想的案例。我的用法是四步：收集 → 归类（看哪类问题错得最多）→ 针对性修（补知识库、改 Prompt、加规则或转人工）→ 放进回归测试，确保改完不再犯。这是运营最日常也最有价值的工作，因为它是用户真实反馈。」
26怎么提升用户留存 / 活跃？
「先定义什么叫『有效使用』，比如完成一次有价值的对话，再看次日和 7 日留存。提升主要三件事：第一次体验要给到惊喜，别让用户问三句就放弃；把最高频的场景做成模板或快捷入口，降低使用门槛；定期用新能力或新内容把用户唤回来。留存是体验问题，不是运营活动能硬拉起来的。」
27让你来运营我们的 AI 产品，第一步做什么？
「先不急着做功能。先看现有数据和真实对话记录，搞清楚现在谁在用、卡在哪、最高频的三个问题是什么；然后挑一个『高频、有价值、又好落地』的场景做样板，跑出效果再复制。先止血，再做增长，别一上来铺摊子。」
28怎么从 0 到 1 推一个新功能上线？
「五步：先验证需求是不是真的（访谈加数据）；定清楚成功指标是什么；做最小可用版本；小流量灰度，看数据、收反馈；再决定放大、迭代还是下线。最关键的是先定『什么叫成功』，否则上线了也不知道好坏。」
29什么是 A/B 测试？要注意什么？
「把用户随机分成两组，只改一个变量，跑够样本量，看核心指标差异是不是显著。三个坑：一次改好几个东西说不清是谁的功劳；样本太少就下结论；只看点击这种浅指标，不看留存和满意度。」
30用户投诉 AI 答错了，你怎么处理？
「先安抚、直接给正确答案，别让用户等；然后把这条记录成 badcase；查是知识库缺、Prompt 没约束、还是模型能力问题；修完回归验证。如果同类问题反复出现，就给这类问题加兜底话术或者直接转人工。」
31怎么设计一个 Agent 的人设和话术？
「定三件事：身份（你是谁、能帮什么）、语气（正式还是亲切，最好给几个例句）、边界（什么能答、什么必须拒或转人工）。再写一批『标准问法 → 标准答法』当示例，建一个话术库持续维护。语气要一致，别一会儿官方一会儿卖萌。」
32怎么控制 AI 产品的成本？
「三个杠杆：少喂——检索更准、上下文别塞太多；换模型——简单任务用小模型，难的才上大模型；做缓存——高频问题的答案直接缓存。另外控制回答长度、减少不必要的工具调用轮次，也能省不少。」
33怎么做竞品分析？
「选三到五个直接竞品，按目标用户、核心场景、关键功能、定价、体验短板做一张对比表。重点不是罗列功能，而是找『他们没做好、我们能切入』的点，最后要落到结论和行动建议上，不然就是抄了一堆截图。」

D. 项目追问34–41

34介绍下你的项目（掌柜智库）
「是一个面向零售行业的企业知识库问答系统。它把商品 PDF 手册自动解析、切块、向量化存进向量库，用户用自然语言提问，系统先检索相关资料再让大模型基于资料回答，还能调工具查价格、做产品对比、必要时联网补充。主要解决的是——企业文档太多，人找不到，AI 又容易瞎编。」
35这个项目里你具体负责什么？
「我主要负责查询这条链路（或如实说清你负责的模块）：用户提问后怎么确认商品名、怎么并行去检索、结果怎么融合排序、最后怎么控制喂给模型的上下文。导入和部署那部分是团队其他人做的，我了解它的作用但没亲自改。」 诚实最重要。被追问没做过的模块，就说「这块我没亲自改，但我知道它是为了解决 XX」。
36项目里最难的点是什么？
「最难的其实是让答案『可信』。一开始检索回来的资料里混着无关内容，模型就会照着编。我做了两件事：一是检索用多路召回再融合，提高找全的概率；二是重排后不固定取几条，而是按分数明显下降的位置截断，只给最相关的。改完之后，答错的情况明显少了。」
37如果重做一次，你会怎么改？
「我会更早建评测集。当时是边做边凭感觉调，后来才发现应该先有一批标准问答，每次改完都能量化对比，不然容易『感觉变好了其实没变』。另外我会把 Prompt 和配置抽出来做版本管理，方便回滚和对比。」
38这个项目上线了吗？效果怎么样？
「目前是（如实说：课程/个人/内部试用）阶段。效果上我用一批真实问题做过对比，主要看的是答案有没有出处、答不出来的比例、以及答错的情况。没有精确的商业数据，但 badcase 比最初版本少了很多。」 别编「提升了 40%」这种没依据的数字，一追问怎么测的就崩了。
39为什么选 Milvus / BGE 这些技术？
「选型主要看三点：中文效果、是否开源可控、部署成本。BGE 系列在中文检索上效果比较稳、开源免费；Milvus 是成熟的向量库，支持大规模数据、也支持稠密加稀疏的混合检索。对我们这种要处理大量商品文档的场景够用，也不至于被某家云服务绑死。」
40这个项目你最大的收获是什么？
「最大的收获是理解了『AI 产品不是模型越强越好』。同样的模型，资料喂得对不对、上下文干不干净、规则写没写清楚，效果差得非常远。这让我更想做运营——因为这些问题都发生在模型外面，是运营能改善的。」
41你这个项目和我们岗位有什么关系？
「关系很直接。你们要做 AI Agent，核心就是三件事：知识怎么喂、Prompt 怎么写、效果怎么测——我在项目里都实际踩过。而且我知道哪里容易出问题，比如资料混进无关内容会导致瞎答、模型返回格式偶尔会飘，这些经验能让我上手更快，不用从零试错。」

F. 场景与实操题50–56

50如果让你给我们做一个客服 Agent，你会怎么做？★
「我会按八步讲。第一，定目标指标，比如自助解决率、满意度。第二，摸清用户和最高频的三个问题。第三，划边界，哪些它答、哪些必须转人工。第四，整理知识库，把 FAQ、产品文档清洗入库。第五，设计流程，意图识别→查资料→必要时调工具→回答→兜底。第六，写 Prompt，定角色、语气、禁止事项。第七，先小范围试用，建 badcase 库。第八，按周看数据迭代。」 技巧：讲完骨架就停，等对方追问细节，不要一口气背完。
51给你一段 Prompt，你会怎么优化？
「先问目标是什么、现在哪里不满意。然后按公式补：角色、任务、约束、示例、输出格式。把模糊的话改成可检验的规则，比如『回答友好一点』改成『用两句话以内、语气亲切、不超过 60 字』。改完拿同一批问题跑一遍，对比前后效果，而不是凭感觉。」
52给你一份用户对话数据，你怎么分析？
「先明确要回答的业务问题，再检查数据口径和质量。然后做三件事：统计高频问题看用户到底想要什么；看哪些问题答得差（用户追问、差评、转人工）；看漏斗，用户在哪个环节流失。最后给结论和能落地的建议，不是甩一堆图。」
53用户问了一个知识库里没有的问题，Agent 该怎么答？
「明确告诉他『这个我暂时查不到』，绝对不编。然后给替代方案：转人工、留联系方式、推荐相关的问题。同时把这条记进 badcase，回头补知识库。宁可说不知道，也不能给个错的答案——用户被骗一次就不信了。」
54怎么让 Agent 回答得更像人？
「少用『根据您的问题』这种模板腔；句子短一点、口语一点；必要时先追问澄清；适当给具体例子。但要注意——客服场景准确比亲切重要，不能为了像人而牺牲准确，更不能瞎聊跑题。」
55老板要你一周内上线一个 Agent，你怎么做？
「先砍范围：只做最高频的一个场景，不做大而全。用现成平台（扣子、Dify）先搭，知识库用手头资料，先内部试用再小范围放开。同时跟老板对齐预期——一周能上的是『可用版』，不是完美版，后面按 badcase 迭代。」
56如果让你配合做产品演示 / 会销，你怎么准备？
「先搞清楚台下是谁、他们最关心什么。演示只讲一个痛点场景，用真实问题现场跑一遍，别念功能列表。准备三个『必成功』的问题保证效果，再准备一个兜底方案防止翻车。演示完留资料和联系方式。演示的成功标准是客户听懂并且想试，不是技术多炫。」 提示：这家公司在招会务销售，这题很可能问到，结合公司答会加分。

「先听清他为什么这么想，很多时候分歧是因为信息不一样。能用数据或小实验验证的就验证，不争输赢。实在定不下来就按负责人的决策执行，事后复盘看谁对。重点是别把分歧变成情绪。」
65你最近在学什么？
「在补 Agent 编排这块，比如 LangGraph 怎么把多个步骤串起来；也在自己搭一个小场景的 Agent 练手。另外在系统看一下 AI 产品的评测方法，因为我觉得这是运营最该会、但很多人不会的部分。」 别说「在学 AI」这种空话，要说具体在学什么、为什么学。
66你还有什么想问我们的？
「有三个想了解：一是咱们 AI Agent 这条线现在主要面向什么场景或客户？二是运营岗进去第一个月主要负责哪块？三是团队现在对 Agent 效果是怎么评估的，有没有在跑的评测指标或者 badcase 流程？」 别问薪资、别问加不加班、别问能不能远程——这些留到 offer 阶段。问业务和岗位内容，显得你关注的是做事。

17FDE 专项 · 岗位变了，准备也要变HR 已确认，按这个准备

先搞懂：FDE 到底是个什么岗？

FDE = Forward Deployed Engineer，前置 / 驻场交付工程师，最早是 Palantir 的岗位模式，现在 AI Agent 公司普遍在用。一句话：驻到客户现场，把公司的通用产品改造成客户能用的系统。

它介于三种角色之间：比纯开发多见了客户、比纯实施多了改代码、比售前多了对交付结果负责。HR 说的三个关键词翻译过来就是：

  • 「线下部署」= 不是 SaaS 开箱即用，要进客户的环境（常常是内网 / 私有化），装、配、调、教。
  • 「按客户情况搭建」= 每家客户的数据、流程、术语都不一样，要现场梳理需求再配置，没有标准答案。
  • 「部分开发」= 写脚本、对接接口、处理数据、改点现成代码——不是让你从零造平台。
这对你意味着什么（三条）：
① 技术分要补回来：Python 从「基本不问」上调为「一定会问」，但仍是脚本级，不是算法级。今晚必须能讲清「怎么调 API + 怎么处理 JSON/CSV + 怎么对接一个接口」。
② 新增三类必考题：能不能出差驻场、客户需求不明确/老改怎么办、现场出了故障怎么救。
③ 你的项目价值变高：它证明你「能独立把一套东西从零搭起来」，这正是 FDE 最看重的。讲的时候强调「我自己搭起来、自己调通、自己排错」，而不只是懂概念。
F1你怎么理解 FDE 这个岗位？★
「我理解是驻在客户现场的交付工程师。公司的产品是通用的，但每个客户的数据、流程、说法都不一样，FDE 就是到现场把它调成客户能用的样子——梳理需求、配置和写 Prompt、对接他们的系统、写点脚本、培训客户，上线后还要继续维护。跟纯开发比要多见客户，跟纯实施比要能改代码，跟售前比要对最终能不能用起来负责。」
F2能接受出差 / 驻场吗？★
「可以，我时间比较灵活，南通本地和周边都能跑。驻场我反而觉得是好事——能直接看到客户怎么用、卡在哪一步，比在办公室里猜有用得多。」 如果你确实不能长期驻场，一定要诚实说边界：「短期驻场没问题，长期的话希望提前沟通」。别先答应后反悔，这行最忌讳这个。
F3客户需求说不清楚、还一直改，你怎么办？★
「三步。先用客户的话把需求复述一遍确认——『您是不是想要这个效果？』，把模糊的要求变成可以验收的标准；然后说清这一版做什么、什么时候交付，超出的记下来排到下一期；每次变更留个记录，让客户确认。不是不做，是让它有节奏，否则永远交付不了。」 核心：管预期，不是拒绝客户。
F4客户环境受限——没外网、数据不能出内网，怎么办？
「先在方案阶段就问清楚三个约束：能不能连外网、模型能不能用云 API、数据能不能出内网。能私有化就本地部署开源模型和向量库；不能联网就把联网能力关掉，只做本地知识库问答；数据敏感就做脱敏和权限控制。这些必须提前问，别到了现场才发现装不了。」 这就是 FDE 和纯运营的区别：你要懂环境限制。
F5你的开发能力到什么程度？能独立做吗？
「能写 Python 脚本做数据处理和接口对接，能调大模型 API，能看懂并修改现成代码，能部署和排查常见问题；复杂的前端和后端架构我不行，需要团队支持。我的定位是——常见的脚本和对接我自己扛，超出能力的提前说，不硬撑到交付前才爆。」 别答「我什么都能写」。FDE 面试官一定会追问「那你写个 XX 试试」，诚实分级反而显得可靠。
F6客户当着你的面说「你们这 AI 根本不好用」，怎么办？★
「先不解释，先看具体 case。请客户给两三个真实问题，我当场跑一遍，判断是知识库缺资料、Prompt 没约束住、还是检索没找到。能当场修就修，修不了先给临时兜底——转人工或者标准话术，同时明确告诉他什么时候给正式方案。回去把这个 case 记下来做回归测试。现场最重要的是让客户觉得你在解决问题，而不是在解释为什么做不到。」
F7交付时间特别紧，做不完怎么办？
「先砍范围，保住核心场景能跑通；然后同时跟客户和公司同步——这一版能做什么、不能做什么、下一期补什么。宁可先上一个能用的版本，也别为了追求完美延期。上线后按真实使用情况迭代，比闷头做完再给客户看要稳。」
F8客户员工不会用、甚至抵触 AI，怎么办？
「培训要落到他们自己的场景里，用他们自己的数据演示，别讲功能。先让一两个愿意用的人用起来，做出效果，再让他们去影响其他人；同时把高频操作做成模板或快捷入口，降低门槛。抵触往往是因为怕麻烦或者怕被替代，得先让他们尝到省事的甜头。」
F9客户的数据安全怎么保证？
「最小权限、敏感字段脱敏、操作留日志、按需做数据不出内网。跟客户明确哪些数据会被用到、存在哪里、谁能看。这块我会严格按公司规范来，拿不准的先问，不自作主张。」
F10客户提了一个明显不合理的需求，你怎么办？
「先搞清楚他背后真正想解决什么——他要的往往不是这个功能。能给替代方案就给替代；确实做不到的，明确说不，同时说明原因和别的路径。不硬顶，也不乱承诺，因为承诺了做不到，最后丢的是信任。」

FDE 岗要反过来问 HR 的 4 个问题（很重要）

  1. 交付主要在本地还是外地？出差/驻场的频率大概多少？（判断你能不能接受）
  2. 客户以什么类型为主？是私有化部署还是云端？（判断技术难度）
  3. 「部分开发」具体指什么——写脚本、对接接口，还是要改前端？（判断你的能力是否够）
  4. 新人有没有人带？我进去第一个项目大概是什么类型？（判断成长环境）

另外提醒：4–6K 招 FDE 偏低，说明这是初级/培养岗——他们不会指望你独立扛大项目，而是希望你学得快、能跑现场、肯干活。别被「涉及开发」吓到，也别把自己包装成高级工程师。定位成「能落地、肯跑现场、学得快」最合适。

还要留个心眼（自己判断，别在面试说）：

公司同时在招会务销售，「AI Agent 运营 + FDE 线下部署」很可能兼着售前支持和现场陪访，甚至带一点销售性质。面试时可以从「这个岗位的考核指标是什么——是交付验收，还是也有业绩要求？」这句侧面问出来。你自己要想清楚能不能接受经常跑客户、做演示、被客户挑毛病。
